01

The recommendation

One question drives this: how do we let a team run the whole solution — UI, API, and agent runners — with the least friction, while keeping the door open to scale?

Recommended architecture

A TypeScript monorepo, shipped as a single Docker Compose stack.

One repo with shared types across the frontend/backend seam. One docker compose up brings up the web app, the API + real-time gateway, the orchestrator, Postgres, Redis, and a pool of containerized agent runners. The same images deploy to a single cloud host or scale out to Kubernetes unchanged.

1 repo, shared contracts 1 command to run TS end-to-end containers for agent isolation compose → k8s same images

Everything below justifies and details this. The headline benefit: the contracts in the two integration briefs become shared TypeScript — the frontend and backend literally import the same entity and event types, so the seam can't silently drift.

02

Why this shape

Four principles, each chosen for "simple to distribute" first and "scales later" second.

◇ One deployable unit

The UI is static files served by the API; the whole system is a short list of containers in one compose file. Nothing to wire up by hand.

⇄ Shared contracts

A single shared package holds entity + event types. Both sides import them — the integration briefs become code, not prose.

≋ Real-time first

A WebSocket gateway + Redis pub/sub is the backbone, not an add-on — it's what makes the flight deck feel live for every operator.

▣ Isolated runners

Agents run real commands. Each runner is its own container — clean isolation, natural busy/idle lifecycle, easy to cap and scale.

Why TypeScript end-to-end The frontend is already React/TSX. Making the backend TypeScript too means one language, one toolchain, and — critically — one set of types shared across the wire. For a small team shipping fast, that coherence outweighs the raw throughput a separate Go service might add (and the orchestrator can still be split out later — see §10).

04

Monorepo & shared contracts

One repository, a few workspaces, and a shared package that both sides depend on. This is what keeps the frontend and backend honest.

tower/                      # pnpm workspace monorepo
├─ apps/
│  ├─ web/                  # React + Vite SPA (the current UI, ported)
│  └─ server/               # API + WS gateway + orchestrator
├─ packages/
│  ├─ shared/              # ◀ entity types + event schemas + zod validators
│  └─ runner-sdk/           # the provider-agnostic runner interface
├─ docker-compose.yml       # web · server · postgres · redis · runners
└─ Dockerfile               # multi-stage: build web → serve from server

The shared package is the spine. The entity shapes from the Backend Brief §03 and the events from §07 live here once, as TypeScript types plus runtime validators:

// packages/shared/src/contracts.ts
export type AgentStatus = 'running' | 'waiting' | 'review' | 'done';
export interface HitlItem { id; agentId; kind; title; why; raisedAt; … }
export type ServerEvent =
  | { type: 'hitl.raised'; item: HitlItem }
  | { type: 'agent.progress'; agentId; progress; plan }
  | …;   // the §07 event union — one source of truth
Payoff Change a field and both apps fail to compile until they agree. The integration briefs stop being documents you have to keep in sync by hand — the compiler enforces them.

One image, two roles A multi-stage Dockerfile builds the web SPA and copies it into the server image, which serves the static files and the API/WS. One artifact to ship; the proxy only exists to terminate TLS and (at scale) load-balance replicas.
06

Real-time fan-out

The flight deck is only useful if it's live for everyone watching. Redis pub/sub behind the WebSocket gateway makes that work across multiple operators and multiple app replicas.

1
Something changesAn agent logs a line, progresses, or raises a blocker; the orchestrator writes to Postgres.
2
PublishIt publishes a typed ServerEvent to a workspace-scoped Redis channel.
3
Fan outEvery API replica subscribed to that channel pushes the event down its open WebSockets — all operators update at once.
4
ReconcileClients applied a snapshot on connect; now they patch per event. (Exactly the model the UI is already built for.)

Redis also holds the authoritative HITL raisedAt timers and a short-lived cache, so wait times are consistent across operators rather than each browser counting on its own.

07

Runner isolation

Agents execute real commands and touch real repos. Each runner is its own container — the cleanest answer for safety, lifecycle, and scale.

  • Isolation & safety. A contained blast radius for the commands behind APPROVAL items; resource caps per runner.
  • Natural lifecycle. "Provision a runner" = start a container; "retire" = stop it; busy/idle = has a live agent or not. The Backend Brief's state machine maps 1:1.
  • Provider-agnostic. Each container wraps one provider CLI behind the runner-sdk interface (start/pause/resume/message/fork/stop), so the orchestrator never special-cases a vendor.
  • Scales independently. The runner pool grows on its own axis — more hosts or a k8s node pool — without touching the app tier.
Start simple On a single host, runners are Docker containers the orchestrator manages via the Docker API. Reach for Kubernetes Jobs / a node pool only when one host runs out of room — the runner-sdk boundary means that swap doesn't touch the rest of the system.

09

Migration from the prototype

The current artifact (in-browser React + Babel) becomes apps/web with little structural change.

1
Lift to ViteDrop the in-browser Babel + window.* exports; the .jsx modules become real imports. Component logic is unchanged.
2
Extract contractsdata.jsx's shapes move to packages/shared as types; the mock constants become seed/fixtures.
3
Swap the data sourceThe lifted state in app.jsx reads a snapshot + event stream instead of seed arrays; handlers (§08 of the Frontend Brief) call the API instead of mutating local state.
4
Stand up the serverPersist the four collections, implement the API + WS, then the orchestrator + one runner — exactly the Backend Brief's build sequence.
10

Alternatives considered

OptionVerdict
Separate Go orchestrator from day oneLater, not now. Real concurrency upside, but a second language + duplicated types slows a small team. The runner-sdk seam lets us extract it once throughput demands it.
Serverless (functions + managed WS)No. Long-lived agents, persistent connections, and stateful orchestration fight the serverless model; cold starts hurt the live feel.
Two separate repos (web / server)No. Loses the shared-types payoff and complicates versioning the wire contract — the opposite of "simple to distribute."
Electron / native desktop wrapperNot needed. The web app already feels like a desktop app; a browser + PWA covers desktop and mobile without a separate build.
Kubernetes from the startOverkill to begin. Compose covers self-host and small cloud; the identical images move to k8s when scale calls for it.
In one line Optimize for a team that wants to git clone and docker compose up today, with a clean path to replicas, managed data, and a k8s runner pool tomorrow — no rewrite in between.
