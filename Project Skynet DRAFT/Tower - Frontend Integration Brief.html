01

What we built

A non-IDE supervision console for running a fleet of coding agents in parallel. It answers the three operator questions: what needs me right now, where is each task, and who is working on what.

Tower is a "flight deck," not a code editor. Operators don't read files — they review plans, decisions, approvals, and diffs, then unblock agents so work never stalls. The codebase is shown code-agnostically: as named architectural modules (Billing, Auth, Shared UI…) rather than a file tree.

02

Real vs. stubbed

The single most important thing for the frontend team: the interface is real and complete, but it runs on in-memory mock data and a fake activity loop. Nothing talks to a server yet.

✓ Real & interactive (built) Full navigation; all five home lenses; Inbox triage with approve / reject / modify / chat / pick-option; project CRUD; task backlog CRUD; "assign" spins up an agent on an idle runner; fleet configure / retire across 5 providers; agent detail with plan, log, live preview, fork; status-bar drill-downs; clickable conflict + dependency display; tweakable theme/density.
◌ Stubbed — needs a backend (wire these) Persistence (all state resets on reload) · agent execution (assigned agents get a canned 4-step plan + simulated log, they don't really run) · chat (echoes a single canned reply) · dependency & conflict detection (display-only from static data, not computed) · live preview (rendered mock per known agent id, not a real build artifact) · heartbeat (a static number, doesn't tick).

Everywhere the UI calls a handler (see §08), the handler currently mutates React state. Each one is a drop-in seam for a real API call.

05

The HITL model

The heart of the product. An agent that needs a human raises a queue item of one of four kinds; the operator resolves it and the agent resumes immediately. This is the contract the backend must speak.

KindBadgeRaised when…Extra payload
approvalAPPROVALAgent wants to run a risky action (migration, command)command
questionDECISIONAgent needs a choice to proceedoptions[], recommended
planPLAN REVIEWAgent wants sign-off before executing a plansteps[]
diffDIFF REVIEWWork is ready to mergediff {add, del, files[]}

Resolution actions

Every card resolves through one handler, resolve(queueItemId, action):

'approve'Accept; agent resumes. For diff kind this merges and marks the agent DONE.
'reject'Decline; agent revises its approach and resumes.
'modify'Operator types an adjusted instruction; agent resumes with that guidance. (Inline composer.)
'option-N'For question kind — operator picked option index N.
chatDiscuss before deciding without resolving — the agent keeps working meanwhile. (Does not call resolve.)
Design decisions baked in Cards never resolve from a list with bare buttons alone — full context travels with the card, and the whole card is clickable through to the task. Modify and Chat are first-class alongside Approve/Reject (an explicit requirement). Queue is sorted oldest-wait first.

Supporting maps

  • MODULES — module id → friendly name ('api/billing' → "Billing"). The code-agnostic layer; nothing renders raw paths.
  • DEPS — { from, to } agent-id pairs powering Timeline connectors and gating.
  • AREAS — module id → file count (sizing only).
  • RUNNERS — agent id → runner name (window.RUNNERS, mutated when agents spin up).
07

State & data flow

All live state is lifted into App (app.jsx). Views are presentational — they receive data and callbacks as props and never hold domain state.

// app.jsx — the four live collections
const [agents,   setAgents]   = React.useState(AGENTS);
const [queue,    setQueue]    = React.useState(QUEUE);
const [projects, setProjects] = React.useState(PROJECTS);
const [fleet,    setFleet]    = React.useState(FLEET);

window.LIVE_PROJECTS = projects;  // helpers resolve names against current state

The live simulation (toggleable via Tweaks → "Live activity") runs two intervals. Replace both with your real-time transport (WebSocket / SSE / poll):

LoopNowReplace with
1s tickIncrements queue[].waitedServer-authoritative wait time, or compute from a raisedAt timestamp client-side
4s log pollAppends canned lines from LOG_POOL & nudges progressStreamed agent log lines + real progress/heartbeat events
Persistence is the #1 wire-up Every CRUD and resolve mutates React state only — a reload restores the seed data. Back the four collections with your store/API before anything else; the rest of the integration hangs off that.
08

Integration surface (the API)

These handlers are defined in App and threaded to views as props. Each is a clean seam: swap the local state mutation for a backend call (optimistic update or await + refetch — your call).

HandlerFires whenBackend needs to…
resolve(id, action)Operator resolves a HITL itemDeliver the decision to the agent & resume/merge it
createProject(p)New projectPersist project, return id
updateProject(id, patch)Edit goal/namePersist patch
deleteProject(id)Delete projectDelete + reassign/stop its agents
addTask / updateTask / deleteTaskBacklog editsPersist the backlog list
assignTask(pid, idx)"Assign" a backlog taskProvision a runner & start a real agent on the task; return the agent
configureAgent(r)Add a runner in FleetRegister the runner with the provider/credentials
updateAgent(rn, patch)Edit a runnerPersist config (model, etc.)
retireAgent(rn)Retire a runnerTear down (guarded: busy runners blocked in UI)
openAgent / openProjectNavigationNothing — pure client nav

Two behaviors that aren't single handlers but need backends: chat (the composer in QueueCard / AgentDetail currently echoes one canned reply — point it at the agent's conversation channel) and Fork agent (the button in AgentDetail — should duplicate an agent with shared context onto a new runner; the data model already supports it via fork / branchFrom).

Component & file map

In-browser React via Babel — no build step. The HTML loads React, then the JSX modules in order. Components export to window to share scope across files.

Productionizing the stack The in-browser Babel setup is ideal for design iteration, not for shipping. For the integrated app, port these modules into your real toolchain (Vite/Next + JSX), replace the window.* exports with imports, and lift the four collections into your state layer. Component logic transfers directly.

Visual language

Dark mission-control aesthetic. Type and color carry meaning — status and provider colors are semantic, not decorative.

TokenValueUse
Display / UISpace GroteskAll interface text
MonoIBM Plex MonoIDs, runners, branches, logs, metrics
Accent (signal)#FFB224 amberPrimary action, "needs you", brand — tweakable
Running● green #3DD68CAgent working
Blocked / waiting● amber #FFB224Needs a human
Review● blue #5EA2FFDiff/plan ready
Done● greyMerged / complete

Density is tweakable (compact / regular / comfy) via a data-density attribute and spacing variables. Minimum body type holds at a legible size; the dark palette and restrained accent keep a dense fleet readable. No emoji as UI — provider glyphs are typographic marks.

Open questions & recommended sequence

Suggested order to turn the prototype into the integrated product.

1
Persistence + read APIBack the four collections (agents, queue, projects, fleet). Everything else depends on this.
2
Real-time transportReplace the two sim loops with streamed log / progress / heartbeat / new-blocker events.
3
HITL round-tripWire resolve() to actually deliver the decision and resume/merge the agent. Highest operator value.
4
Agent lifecycleMake assignTask & Fork provision a runner and start a real agent; enforce the busy-runner retire guard server-side.
5
Chat channelConnect the discuss composer to the agent's real conversation.
6
Computed conflicts & depsDerive module conflicts and task dependencies from real agent activity instead of static data.
7
Live preview sourceDecide how a project's "aimed delivery" preview is produced (deploy URL, build artifact, screenshot service) and which projects qualify as visual.

Decisions we need from product / backend

  • Routing model — do we need shareable URLs / deep links for views, projects, and agents?
  • Auth, workspaces, and multi-operator presence (the avatar/workspace switcher are visual today).
  • Decision audit trail — should resolved HITL items be reviewable after the fact? (Not built.)
  • Capacity policy — should the UI nudge to spin up runners when the queue backs up? (Hooks exist, behavior doesn't.)
  • Source of truth for "modules" — derived from repo structure, or curated?
  • Mobile: project notes call for shipping the app as an installable, Inbox-first PWA — confirm scope.
