01

What the backend owns

Mission Control is a thin, real-time view over a fleet of coding agents. Everything that makes those agents actually run lives in the backend. None of it exists yet — this is a greenfield engine behind a finished UI.

The backend is responsible for five things:

◷ Orchestration

Provision runners, start agents on tasks, track their state, fork them, retire them, reconcile capacity.

⏸ HITL routing

Catch when an agent blocks on a human, raise a queue item with full context, deliver the operator's decision back, resume the agent.

≋ Real-time state

Stream logs, progress, heartbeats, status changes, new blockers, and completions to every connected operator.

▤ Persistence & API

Store projects, tasks, agents, fleet, and decisions; expose CRUD + actions the UI already calls.

Code-agnostic contract The UI never shows raw file trees or unstructured diffs. The backend must expose work as named modules (architectural components) and structured diff summaries (counts + module list), not paths. Keep the file system an implementation detail.

03

Domain model & persistence

These shapes already drive the UI (see the Frontend Brief §06). The backend should persist them — adapt names freely, but the UI expects these fields. Below are the storable entities with the fields that matter server-side.

Agent (a running unit of work)

Agent {
  id, projectId, name,                 // name = the task it owns
  status: 'running'|'waiting'|'review'|'done',
  runnerId,                            // which fleet runner executes it
  provider, model,                     // e.g. 'claude' / 'opus-4.5'
  branch,                              // vcs working branch
  modules: ['api/billing', …],          // architectural areas touched
  progress: 0.0–1.0,
  plan: [{ text, state: 'done'|'now'|'todo' }],
  modifiedFiles: […],                  // surfaced to UI as modules, never paths
  startedAt, lastHeartbeatAt,          // UI shows elapsed + seconds-since-beat
  parentId, branchFromStep             // set when forked (shared context)
}

Project · Task (backlog) · HITL item

Project { id, name, goal, agentIds: […], status }
Task    { id, projectId, text, state: 'backlog'|'assigned'|'done', agentId? }

HitlItem {
  id, agentId, kind: 'approval'|'question'|'plan'|'diff',
  title, why, risk: 'low'|'medium'|'high',
  raisedAt,                            // UI derives "waited" from this
  resolvedAt, resolution,              // audit (see §05 + §11)
  // kind-specific payload:
  command,                             // approval
  options: […], recommended,           // question
  steps: […],                          // plan
  diff: { add, del, modules: […] }     // diff (summary only — no raw patch in UI)
}

Fleet runner · Module · Dependency

Runner { id, name, provider, model, status: 'busy'|'idle', idleSince }
Module { id: 'api/billing', name: 'Billing' }   // the code-agnostic map
Dependency { fromAgentId, toAgentId }       // downstream gated on upstream
Append-only log Each agent has an activity log the UI tails. Store it append-only (timestamp + line) and stream new entries (§07) rather than refetching the whole array.
04

Agent lifecycle

The state machine the orchestrator must implement. The UI renders each state; the backend drives the transitions.

  provision ─▶ running ─┬─▶ waiting ─┐   (HITL: approval/question/plan)
                        ├─▶ review  ─┤   (HITL: diff)
                        │            └─▶ resume ─▶ running
                        └─▶ done       (diff approved / plan complete)
  any running agent ──▶ fork ──▶ new running agent (shared context)
TransitionTriggerBackend work
provision → runningassignTask / forkAcquire an idle runner, clone context, start the agent, emit agent.started
running → waiting/reviewAgent raises HITLCreate HitlItem, pause agent, emit hitl.raised
waiting/review → runningOperator resolvesDeliver decision, unpause, emit hitl.resolved + agent.status
review → doneDiff approvedMerge branch, mark plan complete, free the runner
* → forkFork agentDuplicate context onto a new runner; set parentId
Busy-runner guard The UI blocks retiring a busy runner, but the backend must enforce it authoritatively — reject a retire on a runner whose agent isn't done.
05

The HITL round-trip

The product's core loop, end to end. Latency here is what "develop at the speed of light" depends on — a resolved decision must reach the agent and resume it without a poll cycle.

1
Agent blocksAgent hits an approval / decision / plan / diff gate and calls the orchestrator. Backend creates a HitlItem with full context and pauses the agent.
2
SurfaceEmit hitl.raised. It appears in the Inbox, the Home "needs you" strip, and on the agent — instantly, for every connected operator.
3
Operator actsPOST /hitl/:id/resolve with one of: approve reject modify option-N. Or a chat message (does not resolve).
4
Deliver & resumeBackend hands the decision to the agent: approve → continue; reject → revise; modify → continue with new guidance; option-N → chosen value; diff approve → merge & finish.
5
Confirm & recordEmit hitl.resolved + agent.status; persist resolution + resolvedAt + operator for the audit trail (§11).
Concurrency Multiple operators may view the same item. Resolution must be idempotent & first-writer-wins: a second resolve on an already-resolved item returns the existing resolution, not an error, and the UI reconciles via hitl.resolved.
06

Providers & runners

A runner is a configured agent instance bound to a provider + model. The UI lets operators configure and retire them across five providers; the backend owns credentials, model catalogs, and the actual processes.

✱ Claude Code ◌ Codex ✦ Gemini CLI ▎ Cursor Agent ◈ GitHub Copilot
  • Expose a provider catalog — display name, available models — so the Fleet UI's model dropdown stays server-driven, not hard-coded.
  • Hold credentials per provider/workspace; never surface them to the client.
  • Normalize all five behind one runner interface (start, pause, resume, message, fork, stop) so the UI and orchestrator stay provider-agnostic.
  • Report busy/idle truthfully — capacity hints (§09) and the assign flow depend on it.

09

Derived intelligence

Three signals the UI shows but does not compute. Today they're static mock data; the backend should derive them from real agent activity.

SignalDefinitionDrives
ConflictTwo agent families (excluding a fork and its parent) modifying the same module concurrentlyHome conflict banner; "no double work"
DependencyOne task gated on another's outputTimeline connectors; ordering / gating
CapacityQueued/assignable work vs. idle runnersFuture "spin up more?" nudge (planned)
Fork-aware Conflict detection must treat a forked agent and its parent as the same family — they share context on purpose and shouldn't flag each other. The data model carries parentId for exactly this.
10

Live-preview pipeline

Each project can show its aimed delivery — a rendered preview of what's being built (a running app, a generated doc). The UI embeds it and folds the panel away when there's nothing visual. The backend produces the artifact.

  • Decide the source: an ephemeral deploy URL per agent branch, a built artifact, or a screenshot/render service.
  • Mark which projects are visual (have a renderable delivery) vs. not — the UI hides the panel for non-visual work rather than showing an empty box.
  • Keep it current — the preview should reflect the agent's working branch, updating as work progresses.
  • Expose it as a URL the client can iframe (with appropriate sandboxing / auth).

Cross-cutting concerns

ConcernRequirement
Auth & workspacesOperators belong to a workspace (UI shows the switcher + avatar). Scope every entity, event stream, and credential to it.
Multi-operator presenceSeveral people watch the same fleet. Resolutions broadcast; consider "who's looking at this item."
Decision audit trailPersist every HITL resolution (who, what, when, payload). The UI has no history view yet, but the data must exist to build one.
IdempotencyResolve + assign must be safe to retry (§05). Use the item/task id as the key.
Command safetyapproval items wrap real commands/migrations. Validate, sandbox, and bound them server-side — never trust the client to gate risk.
ScaleDesign for dozens of concurrent agents per workspace; the event stream and capacity logic are the hot paths.

Open questions & build sequence

Recommended order to stand the engine up under the finished UI.

1
Persistence + read API + snapshotStore the four collections; serve them; deliver a connect-time snapshot. Unblocks everything.
2
Event streamWebSocket/SSE with the §07 events. Retire the two client sim loops.
3
Runner interface + one providerNormalize start/pause/resume/message/fork/stop; ship Claude Code end-to-end first.
4
HITL round-tripRaise → resolve → deliver → resume, idempotent, with audit. The core value.
5
Assign + fork + lifecycleReal provisioning, the busy-runner guard, merge-on-approve.
6
Remaining providers + derived signalsCodex/Gemini/Cursor/Copilot behind the interface; compute conflicts & deps.
7
Preview pipeline + auth/workspacesAimed-delivery previews; multi-operator scoping and presence.

Decisions we need

  • Transport: WebSocket vs. SSE + command channel? Hosting/runtime for agents (containers, VMs, per-runner isolation)?
  • VCS model — one branch per agent, merge strategy, who owns conflict resolution at the git level?
  • How is "module" derived — from repo structure, CODEOWNERS, or a curated map?
  • Preview source of truth (deploy URL vs. artifact vs. render service) and its security model.
  • Retention for logs and the decision audit trail.
  • Mobile PWA (project direction) — does it need anything beyond the same workspace-scoped API + stream? (Likely not.)
